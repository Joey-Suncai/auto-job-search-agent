# Auto-apply (orchestrator)

This skill only runs the **general flow** and hands each piece of work to the agent built for it. Answers that depend on the job (start date, location, on-site, years of experience, custom questions) are decided **per job**, not stored here.

| Work | Agent (skill) |
| --- | --- |
| Resume: **A-Classic only**, lightly tweaked for the job description, **with a list of every change** | Resume agent → `skills/resume-updater/SKILL.md` §5 (approved direction master tailored mechanically + truth check; §6 legacy bank pick) |
| Cover letter for **every** application, also when the form has no slot (Joey 2026-11-05) | Cover-letter agent → `skills/cover-letter-writer/SKILL.md` |
| Picking jobs, scores, tracker | `skills/job-hunt-pipeline/SKILL.md` |
| Browser work | `skills/_shared/browser-techniques.md` |

If delegating a job-specific piece, give the worker:
- "Read `<skill path>` and follow it";
- the job description text;
- the company and role;
- the output folder `applications/<YYYY-MM-DD>_<Company>/`.

Batch independent material work when delegation is useful. Avoid starting an agent merely to copy standard answers or make a deterministic headline change. When working inline, follow the resume and cover-letter skills for the materials actually needed. Never skip resume validation.

### The school question and yes/no text boxes (JSA-321 / JSA-322, 2026-11-11)
- **canon school = a positive match.** `config/canonical.json` school `label_re` counts a label only when it asks for
  the school itself ("School", "School name", "enter / select / list your university", "the university you attend",
  "which school do you attend", "your school is not listed"). A label that only mentions a school is not the school
  question (a Greenhouse employer: "the grading scale used by your current school"). "Other" passes when the list (options) holds
  none of his schools; for a "currently attend" question only the current school counts (`canon.other_is_only_pick`).
  Tests: `scripts/test_canon_school.py`.
- **A bare Yes / No goes into a text box only when the box asks a yes/no question** (`rules_bridge.ynTextBox`). The
  work-authorization and sponsorship rules used to be exempt from the text-box guard everywhere, so a Greenhouse employer's "any other
  context … sponsorship" box got "Yes". Tests: `scripts/test_yn_textbox.py`.

### Opt-in boxes (JSA-329, 2026-11-12)
- **"I agree to receive …" is an opt-in, not the data consent.** `answer_rules.js` reads the shape (`OPTIN_SHAPE`:
  agree / consent / would like to receive, sign me up, send me, subscribe, keep me posted) and then what is to be
  received: jobs / openings / talent community → `future_contact` (Yes); campaigns, marketing, events, news, webinars,
  offers, products, surveys, partners → `marketing` (No, also when mixed with jobs); anything else → `optin_other`
  (asked). Messages about his own application / the hiring process / interviews stay the data consent (Yes). Hunt Oil
  11-11 had "recruiting campaign communications" checked by data_consent's bare "I agree". Tests: `scripts/test_optin.py`.

### Materials contract — probe, manifest, gate (2026-10-29)

Materials are **derived from the form, not from the platform's reputation**. Three pieces, in this order:

1. **Probe** — `scripts/materials_probe.py "<app folder>"` writes `requirements.json`: one entry per thing the form
   asks for (resume · cover_letter · essay · transcript · portfolio · other_file), each with the **evidence** that
   produced it (the form's own label + selector) and `required`. Greenhouse is probed offline from `gh_api.json`;
   any other ATS with `--live [--url]` by enumerating file inputs and textareas on the open page (CDP 9222).
2. **Build** — only the skills the requirements name: `resume-updater` always when a resume is asked for,
   `cover-letter-writer` for **every** application — also when the form has no slot (Joey 2026-11-05: 「表单没有放求职信的位置时也要写」); a slot gets it uploaded, no slot keeps it in the folder.
   `scripts/ds_materials.py` writes `materials_manifest.json`: resume file + sha256 + layout result,
   letter decision (`generated` / `not_accepted_by_form` / `skipped_by_joey`) + sha256 + fact-check result, track.
3. **Gate** — `scripts/materials_check.py "<app folder>"` (importable: `from materials_check import check`) returns
   a list of problems: missing manifest, missing file, **sha mismatch** (the file changed after the manifest),
   required cover letter never generated, empty `open_answers.md` for a written question, a required file nobody
   has. Runs before filling; an empty list means the form's requirements are satisfied by what is on disk.
4. **Runners (JSA-002, 2026-10-30; the five newer runners since 2026-11-05, JSA-186 via `runner/presubmit.py`, which also refuses any upload but the folder's tailored resume)** — `run.py` and `run_wd.py` call `runner/materials_gate.py` before filling,
   **default `--materials-gate block`**. A missing `requirements.json` is written first (Greenhouse offline from
   `gh_api.json`; Workday seeded with the resume). Every problem becomes an event for `runner/decide.py`
   (`requirement_appeared` / `material_mismatch`, logged in `decisions.jsonl`, decided once per event); the run goes on
   only on `skip_if_optional` (never for a required item). Anything else stops it with `STATUS blocked` and a queue line
   naming the next step (`generate_material` → run `ds_materials.py`, then rerun). On Workday every page is re-probed for
   file slots other than the resume (cover letter, transcript, portfolio, a second slot): a new one is added to
   `requirements.json`, decided, and stops the run on that page (`status.txt` = needs-user; the tab keeps the filled
   pages). Folders made before 2026-10-29 have no manifest → run `ds_materials.py`, or pass `--materials-gate warn` once
   with Joey's OK.

Tests: `python3 scripts/_test_materials.py` (probe classification, evidence, sha mismatch, missing letter, no-slot
form, missing files) and `runner/_test_decide.py` (event → action menu). Both must print `fails 0`.

## Rules
- **Submitting (his rule, 2026-10-26 21:05):** if every answer comes from the profile, the Standard answers or his earlier answers and nothing is unknown or ambiguous, verify every field and submit without asking; report each submission with its confirmation. Ask first (and wait for 提交) when a field is uncertain, an open-ended answer needs new wording, eligibility is unclear, a consent goes beyond the application, or a password / verification code / new account is needed.
- **Opt-ins and consent boxes (his rule, 2026-10-27):** recruitment marketing emails / marketing communications → **No**; "join our talent community" / keep my information for future roles → **Yes / I agree**; required consent checkboxes at the bottom of the form (privacy notice, data processing for this application) → **check them all**. These need no question. Still ask before creating an account, entering a password, or accepting arbitration / terms that go beyond the application.
- **Accounts (Joey 2026-10-30, replaces the 10-28 rule):** Workday accounts may be signed in to / created automatically by `runner/wd_signin.py`: the password lives only in the macOS Keychain (`jobagent-workday`, account <candidate e-mail>), the script types it, a model never sees it, it is never logged or written. Only the account-terms box of the create-account form is ticked; e-mail verification links / codes come from Gmail read-only (`gmail_code.py`). CAPTCHA, a failed sign-in (e.g. an older account with another password) or a missing Keychain item → the runner waits for Joey as before. Other platforms still: Joey signs in.
- **Close finished application tabs (his rule, 2026-10-28):** as soon as an application is confirmed submitted (by the runner or by Joey), save the confirmation (`runner/save_confirmation.py`) and close its tab — `runner/close_done_tabs.py` closes every tab showing a confirmation / Candidate Home and keeps unfinished forms. Too many open pages slow the browser.
- **Referral first (his rule, 2026-10-28):** before materials or submit, check the role's referral fields (`data/store/jobs.jsonl` `referral` / `contacts` / `warm_path`, `data/store/contacts.jsonl`). Anyone in his network who could refer him → do not apply; tell Joey and wait.
- **Question-type routing (JSA-200, Joey 2026-11-05; problem type: a keyword handed the question to the wrong rule — "visa type" → CPT, "GPA (… not major specific)" → the major rule's "Other"):** `answer_rules.js` first decides what the question asks — from the question sentence only (up to the first "?"), plus the options (GPA bands) — with `qtypes()`, then lets only that type's rules answer. Specific types win and are strict: **gpa**, **visa_type** (→ F-1, never CPT), **auth_kind**; no rule of that type fits, or two specific types → ask Joey. General types (**major**, **degree**, **work_auth** incl. sponsorship) only drop rules of the other typed families; degree + major in one box → ask. A "do you require / need sponsorship / a petition" question is never a visa- or authorization-kind question, whatever examples it lists. Tests: `scripts/test_qtype_route.py` (DeepSeek 26), `scripts/test/t_rules.js`, the form replay (`scripts/learn/replay.py`; 6 submitted answers changed, reasons recorded).
- **Answer-shape check (JSA-201, Joey 2026-11-05):** after a rule answers, `shapeCheck()` in `answer_rules.js` checks the answer looks like an answer to that question type (same `qtypes()` as the routing): a GPA has a number or is N/A / Other; a visa / visa status / classification is a visa or status name — CPT / OPT alone → ask; a major asked alone is not a degree level or a bare Yes/No. **"Other" stays allowed** — Joey picks it when no option holds the fact (decisions-log 10-25 Cadence, 10-30 a Workday employer; Bosch degree BA/BS/PhD/Other → Other is right). Wrong shape → status unknown (`why: answer shape: …`), the runner asks. Tests: `scripts/test_answer_shape.js` (DeepSeek 24), `t_rules.js`; replay unchanged.
